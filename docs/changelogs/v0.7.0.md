# v0.7.0

## Release Date

2026-11-24

## Overview

Adds task schedules and task runs to the client: list, create and delete a space's schedules, read the signed-in user's task consent, start a task chain run and read its log, and read the signed-in user's name. They are announced by a new client capability, `'task-schedules'`. Catalyst-CLI v2.9.0 uses them for the `feed_chain` step of `bdc deploy` and for the new `bdc schedules` and `bdc chains` commands.

## Breaking Changes

None. The change adds methods, exports and one capability name; no existing method changed.

## What's New

### Schedules

- `listSchedules()` returns every schedule of the space, whatever the application (task chains, flows, views): `scheduleId`, `spaceId`, `applicationId` (`TASK_CHAINS` for a task chain), `activity` (`RUN_CHAIN`), `objectId`, `description`, `activationStatus`, `cron`, `owner`, `changedBy`, `changedAt`, `nextRun`, and `timezone`. The tenant responses captured carry no time zone field, so the cron is UTC and `timezone` is `null` unless a record carries one. `cron` is `null` for a schedule defined by a frequency.
- `createSchedule(input)` creates a schedule from `applicationId`, `activity`, `objectId` and `cron`, with an optional `description` (default the object's name) and `activationStatus` (default `ENABLED`). It returns `{ scheduleId }`. The schedule is owned by the signed-in user.
- `deleteSchedule(scheduleId)` deletes one.

Schedules use Datasphere's internal task-framework endpoint, `/dwaas-core/tf/{space}/schedules`. SAP does not document it. The request and response shapes in the code come from tenant responses captured 2026-11-24.

### Task consent, runs and logs

- `readTaskConsent()` returns the signed-in user's consent to run tasks, which a schedule they own needs: `status` (`CONSENT_GIVEN`, `NO_CONSENT` or `CONSENT_EXPIRED`), `createdAt` and `validUntil`. Datasphere lets no one read another user's consent.
- `runTaskChain(chainName)` starts a run and returns its `logId`. The run continues in the background.
- `readTaskLog(logId)` returns the run's `status` (`RUNNING`, `COMPLETED` or `FAILED`), `startTime`, `endTime`, `runTime` (milliseconds), `objectId`, `children` (one per task: `objectId`, `status`) and `messages` (`severity`, `text`).
- `readCurrentUser()` returns the signed-in user's Datasphere user name, the name a schedule's `owner` holds, or `null` when the response has none. The OAuth token carries only the e-mail, so it is read from the session endpoint the Datasphere shell calls when it starts.

Consent, runs and logs use the documented `/dwaas-core/api/v1/tasks` endpoints that SAP's CLI calls.

### `'task-schedules'` capability

`client.capabilities` now lists `'task-schedules'` beside `'task-chain-delete-options'`. A caller tests for it before using the methods above, since an older build lacks them. Catalyst-CLI v2.9.0 checks for it at runtime and errors if the linked catalyst-bdc does not have it.

## Technical Details

- New `core/operations/task-schedule/` (`list.ts`, `create.ts`, `delete.ts`) and `core/operations/task/` (`consent.ts`, `runTaskChain.ts`, `readTaskLog.ts`, `readCurrentUser.ts`), each with an `index.ts` barrel. Responses are validated with Zod and mapped to the exported types, with absent fields as `null`.
- `readTaskConsent` reads the expiry from `validUntil`, falling back to `validTo`, the name in SAP's discovery document.
- `runTaskChain` and `readTaskLog` accept a log id sent as a number or a string; `runTaskChain` returns it as a number and fails if it is not numeric.
- `client/types.ts`: `CLIENT_CAPABILITIES` gains `'task-schedules'`; `BdcClient` gains the seven methods. `client/client.ts` implements them against the configured space.
- `src/index.ts` exports the seven operations and the types `TaskSchedule`, `CreateScheduleInput`, `TaskConsent` and `TaskLog`.
- Tests: new unit test `taskSchedules.test.ts`; `capabilities.test.ts` updated for the new capability.
- Docs: `api.md` gains a "Schedules and Task Runs" section and the capability entry.
