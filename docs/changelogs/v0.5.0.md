# v0.5.0

## Release Date

2026-11-24

## Overview

Adds data access controls: the client can list, read, create, update and delete them. It can also delete a view without forcing, so Datasphere refuses while something still uses it. Catalyst-CLI v2.7.0 uses this so `catalyst bdc deploy` no longer needs SAP's `@sap/datasphere-cli` or its separate sign-in.

## Breaking Changes

None. `deleteView(name)` still sends `deleteAnyway=true`. The new options argument is optional.

## What's New

### Data Access Controls

These use the documented `/dwaas-core/api/v1/spaces/{space}/dataaccesscontrols` endpoints, not the `/deepsea/` import. The paths, parameters and defaults come from the tenant's discovery document, the OpenAPI document SAP's CLI builds its `objects data-access-controls` commands from. Every parameter is sent explicitly, as that CLI sends it.

- **`listDataAccessControls(options?)`**: technical names. Sends `select=technicalName&top=&skip=`. With `top` it reads one page; without it, every page, 25 at a time. `technicalNames` filters.
- **`readDataAccessControl(name)`**: the saved control, `{"definitions": {NAME: {...}}}` (the default `Accept`, all content).
- **`createDataAccessControl(content, options?)`** (POST) and **`updateDataAccessControl(name, content, options?)`** (PUT): the CSN is the JSON body, with `saveAnyway=false&allowMissingDependencies=false&deploy=true` by default (`ObjectWriteOptions`). With `deploy=true`, Datasphere deploys after saving.
- **`deleteDataAccessControl(name, options?)`**: `deleteAnyway=false` by default (`DeleteOptions`), so Datasphere refuses to delete a control that is in use. Note that this default is the opposite of the other types' deletes.
- `objectExists('data-access-control', name)`: `data-access-control` is added to `DATASPHERE_OBJECT_TYPES` (endpoint `dataaccesscontrols`, CSN key `definitions`).

### Deleting a view without forcing

`deleteView(name, { deleteAnyway: false })` sends `deleteAnyway=false`. With no options it still sends `deleteAnyway=true`, so existing callers are unaffected.

### Seen on a tenant (read-only)

- The list returned `[{"technicalName": ...}]`. `skip` pages: `top=25&skip=25` returned `[]` after 19 controls.
- A read returned the `{"definitions": ...}` document.
- A missing control returned 404 `RepoObjNotFound`.

Create, update and both deletes have not been run yet.

The discovery document also lists `/spaces/{space}/taskchains/{technicalName}`, the path v0.4.0 inferred for task chains.

## Technical Details

- New `core/operations/data-access-control/` with `list`, `read`, `create`, `update` and `delete`, exported from the operations barrel. New `core/operations/writeParams.ts` builds the save query. The new operations URL-encode the space and the name.
- New `types/operationOptions.ts` with `DeleteOptions`, `ObjectWriteOptions` and `ListOptions`, exported from the package entry.
- `BdcClient` adds the five control methods and an optional `options` on `deleteView`.
- Tests: `objectTypes.test.ts` checks the new registry entry. `endpointDiscovery.test.ts` adds read-only checks: a missing control is a 404, the list works with `top` and without, and an existing control is read when `DSP_TEST_DAC` is set. A new `dataAccessControlCrud.test.ts` copies `DSP_TEST_DAC` into a scratch control, then creates, reads, lists, updates and deletes it. It also checks that `deleteView(..., { deleteAnyway: false })` is refused while another view reads the view. The integration tests need a live tenant and were not run.
